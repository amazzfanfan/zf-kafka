## 1. 原始系统需求与分析要求

现在我需要开发一个监听RabbitMQ和kafka的web系统，有前后端。主要功能有：
监听RabbitMQ和Kafka这类消息的中间键的消息，然后将这类消息转发到外部的webhook目标源上，主要实现这个功能，当然实现这个功能必须要灵活，要求：
1.任何的webhook都要能转发，这个webhook的定义也要完全能适配，对方的webhook的定义是什么样，都要能无缝的去支持转发到。避免写成只能转发自己认的结果。就是别人的接口开发成什么样，都要能推过去。中间涉及到的问题，比如接口签名，如计算，脚本等一系列问题都要考虑到
2.由于监听的webhook的消息可能非常多，并发可能会很高，这个也要考虑到
3.监听Kafka不能影响原先的业务消费，监听消息转发只是解耦的功能，不能影响原有 的业务系统。
4.要有前后端。接口和页面的路由都要有前缀，接口话要api开头然后紧跟着api的是前缀，页面同理：host端口，然后后面紧跟着前缀。前缀要统一。
技术栈没要求，但是要求性能和资源最佳，以及高并发，低资源
你现在详细分析这个需求。

## 5. 代码、前端与验证检查要求

检查一下：
1. 将每项需求映射到具体代码、前端页面和验证方法，检查是否存在遗漏、空实现、模拟数据或前后端未接通。
2. 重点检查：
   - RabbitMQ、Kafka 是否真正接入，消费隔离是否会影响原业务。
   - Webhook 的 URL、方法、Header、Query、Body 是否可配置，数据转换、自定义脚本、鉴权签名和响应判定是否实际生效，是否存在固定输出结构的限制。
   - 高并发下的并发控制、连接复用、限流、背压和资源边界。
   - 消息确认、持久化、重试、失败重放及进程重启后的恢复是否正确。
   - 页面 /{prefix}/... 与接口 /api/{prefix}/... 是否由统一配置派生；修改前缀后，页面刷新、静态资源和 API 调用是否正常。
