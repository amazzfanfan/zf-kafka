# 实现配置与接口说明

本文字段对应当前代码。设计方案中的示例DSL尚未直接实现，不可混用。

## 1. 消息源

Kafka：

```json
{
  "name":"订单Kafka",
  "type":"kafka",
  "enabled":true,
  "brokers":["kafka.example.internal:9093"],
  "topics":["orders"],
  "group":"relay.orders",
  "start":"latest",
  "tls":true,
  "credential_ref":"已创建的凭证ID",
  "read_bytes_per_second":10485760
}
```

凭证数据：`{"username":"...","password":"...","mechanism":"SCRAM-SHA-256"}`；支持SCRAM-SHA-512和PLAIN。TLS当前使用系统信任根。Group必须是独立的`relay.*`组，同时通过Broker ACL限制只能访问平台组，不能只依赖命名约定。start仅决定无已有提交位置时的初始策略，位点失效报错而非跳过。

RabbitMQ：

```json
{
  "name":"订单RabbitMQ副本",
  "type":"rabbitmq",
  "enabled":true,
  "url":"amqps://rabbit.example.internal:5671/",
  "credential_ref":"已创建的Broker凭证ID",
  "queue":"relay.orders",
  "exchange":"business.orders",
  "routing_key":"order.#",
  "declare":true,
  "queue_max_bytes":268435456,
  "overflow":"drop-head",
  "read_bytes_per_second":10485760
}
```

凭证数据：`{"username":"...","password":"..."}`。URL禁止带用户名密码；vhost按AMQP URL规则编码。

declare=true时只声明平台的durable quorum队列并绑定**已经存在**的Exchange，不创建/修改业务Exchange。Exchange必须具备相应复制语义：topic匹配Routing Key，fanout广播；不会自动把原业务队列变成可复制来源。

overflow必须显式选择：

- `drop-head`：达到容量丢弃最老平台副本，优先降低转发队列对发布的反压；不承诺完整转发。
- `reject-publish`：达到容量拒绝该队列的新消息，可能影响业务生产者确认，必须由业务方接受。

declare=false只消费管理员指定的现有`relay.*`专用队列；容量、绑定、持久化与复制由管理员预置。名称前缀不能替代队列归属检查和专用账号ACL。

手动消息源：`{"name":"本地测试","type":"manual","enabled":true}`。

Source创建后返回id、epoch和默认限制。更新来源必须提交完整原对象，仅允许修改name/enabled；改变Broker、订阅或epoch需新建Source，避免误用旧位置和去重空间。

## 2. 目标与模板

```json
{
  "name":"合作方订单接口",
  "enabled":true,
  "url":"https://partner.example.com/hooks/orders",
  "method":"POST",
  "headers":{"Content-Type":"application/json","X-Event-ID":"{{.DeliveryID}}"},
  "body_mode":"template",
  "body":"{\"orderNo\":{{json .JSON.order_id}},\"amount\":{{json .JSON.amount}}}",
  "auth":{"type":"none","credential_ref":""},
  "timeout_ms":10000,
  "concurrency":16,
  "rps":50,
  "max_attempts":8,
  "success_statuses":[200,201],
  "success_path":"$.code",
  "success_value":0,
  "idempotency_header":"Idempotency-Key",
  "allow_private":false
}
```

body_mode：

- `raw`或空：按源字节透传，不解析后再序列化。
- `template`：Go text/template，配置Body可输出JSON、XML、表单或任意文本；Content-Type由目标定义。
- `script`：调用`buildRequest(ctx)`，返回完整method/url/headers/body。
- `connector`：调用已授权外部构造服务，可使用任意语言与专有SDK。

模板变量：`.JSON`、`.Raw`、`.Metadata`、`.DeliveryID`、`.Timestamp`、`.Nonce`。JSON解析保留json.Number，模板`json`可输出大整数原值。金额建议在源中作为字符串保留；脚本自动把JSON数字转为字符串，避免静默丢精度。

模板函数：`json`、`get`、`queryEscape`、`pathEscape`、`xmlEscape`、`base64`。缺字段失败，不悄悄替换空字符串。

示例表单Body：`order={{queryEscape .JSON.order_id}}&amount={{queryEscape .JSON.amount}}`。示例XML：`<order><id>{{xmlEscape .JSON.order_id}}</id></order>`。

URL路径和Query可模板化，但配置的scheme/host/port固定。脚本不能把请求改到另一个origin。多域名需要分别配置目标，以便执行权限和限流。重定向默认全部禁止，不向新地址泄露签名或Token。

超时100..15000ms，并发1..256，rps大于0且不超过100000，最多20次尝试。RPS令牌桶允许配置速率对应的一秒突发；它不是每个任意滑动窗口的精确次数上限。全局并发由RELAY_MAX_INFLIGHT限制。

默认success_statuses为200、201、202、204。202的含义仅为目标按契约受理，不表示外部业务最终完成。最终异步确认协议未实现。

## 3. 鉴权与签名

先创建凭证，接口仅返回ID，之后配置credential_ref。

| auth.type | 凭证data字段 | 说明 |
|---|---|---|
| bearer | token | Authorization: Bearer |
| basic | username、password | Basic认证 |
| api_key | secret | 默认X-API-Key，可配header/location |
| oauth2 | token_url、client_id、client_secret、scope | client_credentials、Basic客户端认证；按凭证合并刷新 |
| hmac_sha256 | secret | 自定义签名串、hex/base64 |
| rsa_sha256 | private_key | PEM PKCS8或PKCS1私钥，PKCS1v15签名 |
| script | secret | 为请求脚本的HMAC宿主函数绑定密钥 |

HMAC示例：

```json
{
  "type":"hmac_sha256",
  "credential_ref":"凭证ID",
  "canonical":"{{.Timestamp}}\n{{.BodySHA256}}",
  "encoding":"hex",
  "header":"X-Signature",
  "timestamp_field":"X-Timestamp",
  "location":"header"
}
```

canonical可用：Timestamp、Nonce、Body、BodySHA256、Method、Path、Query、Headers。BodySHA256基于实际构造完成的正文；之后不再重新JSON序列化。Query签名前规范化排序并排除签名参数本身；timestamp_field配置为Query参数时先加入再计算签名。`location=query`会将签名放入header指定的参数名。

需要Bearer和HMAC同时使用时，主auth配置Bearer，`auth_chain`配置HMAC数组，按顺序执行；最多4个附加步骤。相同字段后一步会覆盖前一步，配置者应避免非预期冲突。脚本HMAC密钥绑定使用主auth。

mTLS：目标增加`tls_credential_ref`。该凭证可包含`certificate_pem`、`private_key`、`ca_pem`。使用自定义CA也不关闭证书和主机名校验。

## 4. 脚本

仅可信管理员可启用`RELAY_ENABLE_TRUSTED_SCRIPTS=true`。持久子进程池隔离主进程，每次使用新的JS上下文；没有Node/npm、网络、文件、Date和Math.random。每次纯脚本100ms，父进程250ms总期限，超时子进程被替换。

```javascript
function buildRequest(ctx) {
  const payload = JSON.stringify({
    orderNo: ctx.event.json.order_id,
    amount: ctx.event.json.amount
  });
  return {
    method: "POST",
    url: "https://partner.example.com/hooks/orders",
    headers: {"Content-Type":"application/json"},
    body: JSON.stringify({
      payload: payload,
      signature: crypto.hmacSHA256(payload, "base64"),
      timestamp: ctx.timestamp
    })
  };
}
```

ctx提供event.json、event.raw、event.raw_base64、event.metadata、delivery_id、timestamp、nonce。crypto.sha256(text,encoding)、crypto.hmacSHA256(text,encoding)支持hex和base64；HMAC只能使用该目标已授权的签名密钥，不提供读取密钥原文的函数。

二进制请求可返回`body_base64`；平台解码得到实际签名与发送字节。multipart可由脚本构造固定boundary正文并设置Content-Type；没有任意文件系统访问或上传本地文件能力。

目标可另配response_script：

```javascript
function classifyResponse(ctx) {
  const body = JSON.parse(ctx.body);
  if (ctx.status === 200 && body.code === 0) return "success";
  if (ctx.status === 429 || body.code === 1001) return "retry";
  return "dead";
}
```

ctx包括status、headers、body。响应脚本显式替代内置分类，应自行处理状态与业务码；响应正文限制256KiB。

预览使用测试时间上下文、禁用真实鉴权链且不加载密钥。脚本HMAC使用标识明确的虚拟密钥，不可将预览签名当作生产验签结果。预览不会刷新OAuth Token或发外部HTTP请求。

## 5. 规则

```json
{
  "name":"支付订单转发",
  "enabled":true,
  "source_id":"来源ID",
  "endpoint_ids":["目标A的ID","目标B的ID"],
  "filter_path":"$.event_type",
  "filter_value":"paid"
}
```

当前过滤支持对象点路径及JSON值相等，缺失路径报错；没有任意表达式或数组JSONPath求值。单规则1..32个不重复目标，配置对象每类最多128项。多个规则绑定同一目标会生成各自的逻辑投递，需避免意外重复。

接入事务读取一致配置集合并生成目标快照。目标暂停是实时调度开关；重新启用后积压继续用原快照。来源暂停后已持久化任务继续处理。

## 6. API清单

以下均相对于`/api/{APP_PREFIX}/v1`，返回`{"data":...}`或`{"error":"..."}`。除登录与健康检查外需会话或Bearer认证。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST / DELETE | /sessions | 登录 / 退出 |
| GET | /me | 当前管理员与脚本开关 |
| GET | /health/live、/health/ready | 存活 / 数据库就绪 |
| GET | /stats、/source-status | 状态计数 / 当前进程接入状态 |
| GET / POST | /sources、/endpoints、/routes | 列表 / 创建并发布 |
| PUT | /sources/{id}、/endpoints/{id}、/routes/{id} | 完整更新，enabled控制启停 |
| GET / POST | /credentials | 脱敏列表 / 加密创建 |
| GET | /deliveries?before={last_id} | 最新100条 / 以最后任务ID继续翻页 |
| GET | /deliveries/{id}/attempts | 每次执行及UNKNOWN记录 |
| POST | /deliveries/{id}/replay | 终态补投，新任务沿用原快照和幂等键 |
| POST | /deliveries/{id}/cancel | 取消尚未发送的等待任务 |
| POST | /sources/{id}/messages | 手动来源接收body字符串、可选dedup_key |
| POST | /debug/preview | endpoint完整对象、body字符串，纯预览 |
| GET | /audit | 最近100项操作 |

Prometheus指标：`/api/{APP_PREFIX}/metrics`，同样要求认证。页面路径为`/{APP_PREFIX}/`，资源为`/{APP_PREFIX}/assets/`。

示例：手动接收请求体`{"body":"{\"order_id\":\"ORD-1\"}","dedup_key":"test-1"}`。相同来源、epoch、dedup_key在30天保留窗口内只接收一次；不指定则每次生成新消息。

会话保存在服务端内存，12小时到期，浏览器只持有HttpOnly Cookie。重启后重新登录。Cookie写操作校验同源Origin；CLI应使用Bearer。当前单管理员权限模型不代表强多租户隔离。

## 7. 外部连接器协议

当接口依赖特殊SDK或脚本环境没有提供的能力时，配置：

```json
{
  "body_mode":"connector",
  "connector_url":"http://127.0.0.1:8090/build",
  "connector_credential_ref":"连接器Bearer凭证ID",
  "allow_private":true
}
```

同时需要在RELAY_ALLOWED_CIDRS明确放行连接器地址。目标原有url仍是最终Webhook地址；平台不允许连接器把请求改到其他origin。连接器可以构造授权origin下的路径、Query、Header、Body与签名，后续仍可执行原生鉴权链。

平台POST以下对象到connector_url：

```json
{
  "version":1,
  "delivery_id":"逻辑投递ID",
  "idempotency_key":"稳定幂等键",
  "timestamp":"本次秒级时间戳",
  "nonce":"本次随机标识",
  "event":{"id":"...","source_id":"...","raw":"Base64原文","metadata":{},"received_at":"UTC时间"},
  "target":{"url":"https://partner.example.com/hook","method":"POST","headers":{}}
}
```

成功返回HTTP200及**不包装data的**BuiltRequest：

```json
{
  "method":"POST",
  "url":"https://partner.example.com/hook",
  "headers":{"Content-Type":"application/json","X-Signature":"SDK生成的签名"},
  "body":"最终请求正文"
}
```

二进制正文使用body_base64。响应上限1MiB；连接器网络失败、429或5xx会触发持久化重试。连接器调用与目标请求共同受目标总期限约束，连接器应避免不必要的副作用；重复构造时仍需遵循稳定业务数据和幂等约定。

平台不将其他目标的密钥交给连接器。SDK私密材料应由连接器自身的凭证系统保管；平台只使用connector_credential_ref认证构造服务。连接器自身的外部调用和资源限制由其部署负责，不自动获得平台的强沙箱保障。

可运行示例：设置CONNECTOR_SIGNING_SECRET和CONNECTOR_TOKEN后运行`go run ./examples/connector`。示例监听127.0.0.1:8090，演示Body签名包装，替换构造函数即可接入专有SDK。纯预览不会调用连接器，以免触发外部副作用。
